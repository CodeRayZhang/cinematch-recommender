# 本站推荐观察与评估

本轮观测版本：`hybrid-v2.1`。排序公式沿用 [推荐算法指南](recommendation.md)，新增的是缓存和行为观测，并未用虚构线上数据调参。历史 MovieLens 结果保留在独立 [探索评估](recommendation-discovery-evaluation.md) 与 [基线评估](recommendation-evaluation.md) 中。

## 1. 记录什么

仅记录已登录且允许观察的用户。每次推荐请求保存版本、模式、请求时的用户分组、返回电影及位置，API 为卡片返回 `requestId`。游客不建立观察记录，暂停记录后新响应的 `requestId` 为 null。当前默认开启，个人中心可暂停和清除。

| 事件 | 判定和去重 |
|---|---|
| 返回 | 该请求返回的一部电影；不代表用户看到 |
| 曝光 | 卡片至少 50% 进入视口，页面可见且持续 500 毫秒；同一请求 / 电影只记录首次 |
| 点击 | 卡片海报或标题导航；同一请求 / 电影只记录首次，点击也补记曝光 |
| 收藏 | 服务端成功保存想看或看过状态（包含批量操作）后归因；不接收客户端伪造收藏事件 |
| 评分 | 服务端保存本人评分后归因；记录首次评分时间及此后归因更新的星级 |

保存评分自动产生的“看过”状态只计评分，不重复计收藏；撤销恢复不产生新的收藏归因。收藏 / 评分归到该用户同一电影最近 7 天内**最近一次已曝光**的推荐。未曝光、超出 7 天、没有对应返回条目、其他账号的请求，都不能成为有效归因。客户端曝光、点击本质上仍是客户端信号，不是防作弊分析平台。

删除或修改评分并不是一套事件溯源：已记录的首次转化不随取消收藏或删除评分自动撤回；后续归因的评分更新可能修改星级。界面上的“评分 / 高分”因此表示观察记录，不能当作当前所有评分的实时汇总。

## 2. 分组和指标

管理员进入 `/admin` → “推荐观察”，选择最近 7 / 30 / 90 天。统计按**推荐请求创建时间**筛选，按算法版本、模式、请求时已有评分数量分组：

- `new`：0 条评分；可能已有想看、看过或主动类型偏好，并不等于完全没有任何交互。
- `sparse`：1–19 条评分。
- `active`：20 条及以上评分。

用户数为组内去重人数，请求数为组内去重请求，返回、曝光、点击、收藏、评分按“请求 × 电影”统计。高分指观察记录中的 4–5 星。

| 比率 | 分子 / 分母 |
|---|---|
| 点击率 | 已点击条目 / 已曝光条目 |
| 收藏率 | 已归因收藏条目 / 已曝光条目 |
| 评分率 | 已归因评分条目 / 已曝光条目 |

曝光为 0 时比率是 `null`，页面显示 `—`。这些比率不是 Precision / Recall / NDCG，也不是推荐“准确率”。同一用户同一电影在不同请求中可重复曝光，不能直接解释成独立用户转化率。

## 3. 保留和用户控制

每位用户最多保留最近 200 次推荐请求；生成新请求时清理旧记录，同时保证本次刚返回的请求不会被同秒记录排序误删。请求最长保留 90 天，应用启动 60 秒后开始每日清理。清理请求会级联删除其电影观察。

个人中心可关闭新的观察，不影响使用推荐；已有历史保持到清理或手动清除。点击“清除观察记录”仅删除本人的推荐请求和观察，不删除片单、合集、评分、偏好或隐藏列表。只清除而不关闭时，下一次推荐会继续记录。

后台是对保留数据的聚合。活跃用户超过 200 次请求时窗口内较早记录也会被删除；用户主动清除、退出记录或删除电影也会使统计变化。它适合个人项目观察，不能作为不可变审计或完整流量分析。

## 4. 当前能得出的结论

本轮已实现观测链路和契约测试，不生成演示转化率。新库没有记录时显示空状态。自动化测试产生的一次性账号、曝光和评分只存在于隔离测试库，不注入个人数据服务。

仅凭增加埋点，不能声称推荐满意度提升。后续比较应同时报告用户数、请求数、曝光量、用户分组和时间窗口；过滤测试账号，等待至少覆盖完整 7 天归因窗口，避免新请求评分尚未成熟造成误判。

精选 / 探索由用户自己选择，两个组存在自选择差异；不能直接把模式间点击率差异当作算法因果效果。若要正式验证权重变化，需要固定版本、随机分流、预先定义主要指标、按用户聚类比较并保留独立检验期，同时关注收藏、评分、覆盖和冷启动表现。当前没有实现随机 A/B 分流，也没有足够真实使用样本支持效果提升结论。
